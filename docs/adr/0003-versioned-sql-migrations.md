# Versioned SQL Migrations

## Status

Accepted

The schema was bootstrapped by a single idempotent `CREATE TABLE IF NOT EXISTS` block plus an ad-hoc `ensureColumn` probe inside `getDatabase()`. That has no version record, no ordering, no rollback story, and no way to know whether a field database is current — every schema change risked silent divergence between installs. We decided to introduce versioned migrations recorded in a `schema_migrations` table (version, name, checksum, applied_at), applied in order, each inside its own transaction, with the recorded checksum verified on every startup so an already-applied migration that was later edited fails loudly instead of producing divergent schemas in the field. Migration 0001 is the current schema verbatim and stays `CREATE TABLE IF NOT EXISTS`, so adopting the system on an existing field database is a no-op that just records version 1 without touching data, while a fresh database is built entirely by the migration chain. Migrations are authored as TypeScript modules that export `{ version, name, sql }`, not loose `.sql` files: the backend is compiled by plain `tsc` (`rootDir: src` → `dist`) and electron-builder ships only `dist/**/*` plus `package.json`, so `.sql` files would be neither emitted by `tsc` nor packaged without a bespoke copy step, an extra `files` entry, and asar-unpack handling — whereas `.ts` migrations are compiled, packaged, and type-checked automatically with zero added build machinery. Drizzle Kit was rejected for the same reason it does not fit today's reality: it would add a dependency and a parallel migration journal misaligned with the inline-SQL schema that Drizzle only partially models (`users`/`clients`), and the ad-hoc `ensureColumn` approach was rejected because it cannot order, record, verify, or roll back changes.
